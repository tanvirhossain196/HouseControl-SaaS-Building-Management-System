# Bangla and English

Both languages from one set of URLs, chosen with a toggle and remembered in a cookie.

## Why a cookie and not `/bn/...`

Duplicating every route under a language prefix doubles the number of URLs, splits the SEO
between them, and means every internal link has to know the current language. A cookie
costs one thing instead: the marketing pages become dynamic rather than static.

That is the right trade here. The pages are cheap to render, and the alternative is a
person who reads Bangla landing on an English URL somebody shared with them.

The cookie is `hc_locale`, set for a year with `SameSite=Lax`. Not `httpOnly` — no secret
is involved.

## How it is put together

```
src/lib/i18n/locales.ts   the type, the cookie name, parsing
src/lib/i18n/en.ts        English — and the shape everything else must match
src/lib/i18n/bn.ts        Bangla, typed as `Dictionary`
src/lib/i18n/index.ts     getLocale(), getTranslations() for server components
src/lib/i18n/actions.ts   the server action that writes the cookie
```

**A missing translation fails the build.** `bn` is typed as `typeof en`, so leaving a key
out is a type error rather than an English word sitting inside a Bangla sentence.

One detail worth knowing: `en.ts` deliberately has no `as const`. With it, each value's
type is the English string itself, and `"সাইন ইন"` cannot be assigned to `"Sign in"`.
Widening to `string` is what makes the object a shape other languages can fill.

**Switching is a server action**, not `document.cookie`. The cookie is written with the
same flags as every other one we set, and the page re-renders with the new strings in the
same round trip. Writing it from the browser would render English first and correct it a
moment later — a visible flicker on a weak connection.

**`<html lang>` follows the cookie.** It drives screen-reader pronunciation and the
browser's own offer to translate; getting it wrong makes a Bangla page read aloud as
badly-pronounced English.

## What the tests check

Types already guarantee both dictionaries have the same keys. `npm run test:i18n` checks
what types cannot:

- No empty strings in either language.
- **No Bangla string left as its English original** — the failure that happens when
  somebody copies `en.ts` to `bn.ts` and translates half of it.
- Bangla values actually contain Bangla characters.
- A short English label does not become a paragraph in Bangla, which would break the row
  it sits in.
- No stray `{placeholder}` — strings are composed in JSX, so one would render as literal
  braces.
- A tampered cookie falls back to English rather than throwing. That value is editable by
  hand in any browser.

Verified end to end against a running server: the same URL returns
`Every flat, every taka…` with no cookie, `প্রতিটি ফ্ল্যাট, প্রতিটি টাকা…` with
`hc_locale=bn`, `lang="bn"` on the html element, and `lang="en"` when the cookie is
`../../etc/passwd`.

## What is translated, and what is not

**Translated:** the marketing header and footer, the landing page (hero, section
headings, steps, closing call to action), the sign-in and sign-up screens, plan names and
features on the pricing table, and the sidebar labels.

**Not yet:** the interiors of the signed-in app — the dues ledger, the gate console, the
repair timeline, the reports. Those are several hundred strings, and doing them in a hurry
produces the worst outcome: a screen that is half Bangla and half English, which is harder
to read than either.

The way to finish it is one screen at a time: move its strings into `en.ts` under a new
group, add the Bangla, and replace the literals with `t.group.key`. The tests will tell
you immediately if a key is missed.

## Adding a string

1. Put the English in `src/lib/i18n/en.ts`, under the group matching where it appears.
2. Add the Bangla in `bn.ts`. `tsc` will insist.
3. Use it: `const { t } = getTranslations()` in a server component, then `t.group.key`.

For a client component, pass the strings down as props. The dictionary is a plain
serializable object, so it crosses the boundary without a provider.
